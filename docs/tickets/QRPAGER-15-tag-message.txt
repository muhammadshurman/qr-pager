supposed to fail when the value changes. The literals were emitted from the artefact rather
than typed, and tokens:check ties the artefact to the source, so three independent things
must agree before a figure ships.

WHAT THE TESTS CAUGHT BEFORE ANY REVIEWER
===============================================================================

Recorded because each was fixed at the shape rather than the symptom, which is what
QRPAGER-15 §8 asks for:

  - the order-ready colours were THEME ROLES, so "identical in both themes" was false for
    two of the three. Redesigned into a --ready-* namespace emitted exactly once.
  - the lint rule laundered a literal: `padding: var(--space-16) 9px` passed, because the
    value check early-returned on "contains a var()".
  - the same rule's shorthand splitter was a regex lookahead that could not see nesting, so
    clamp(a, b, c) was torn apart and each fragment rejected — found by the GOOD fixture.
  - the rule accepted `color: 'white'` in an inline style object: no hex, no colour
    function, no digit. Colour now has its own allow-list judgement.
  - the CSS scanner walked into node_modules and reported 69 findings in jsdom's own
    stylesheet, because its exemptions matched root-relative prefixes only.
  - focusableWithin filtered on offsetParent and getClientRects, so without a layout engine
    the focus trap trapped NOTHING — the exact failure it exists to prevent.
  - the first font fetch shipped 27 KB twice: Plus Jakarta Sans is a variable font and
    Google serves one file for both weights.
  - one browser check could never have passed: "no element sets outline: none" describes
    every unfocused element in Chromium. Replaced, and the source-level half moved to a
    scan that can fail.

AND FOUR MORE, found by building the generated contrast table rather than spot-checking:

  - DARK alert-ink FAILED AA on two of three dark backgrounds (3.78 and 3.13 against a 4.5
    bar). It was `= approved alert-fill`, and alert-ink is a TEXT role. Escaped because the
    bars table covered three roles.
  - border-strong cleared 3:1 by 0.02 (light) and 0.01 (dark) — the brittleness already
    refused for ink-mid, applied to one role and not the other. Raised to 3.24 and 3.21.
  - THE DANGER BUTTON's label was surface-on-alert-fill at 3.68 against a 4.5 bar: the
    approval allows alert-fill for ">= 24px text only" and the label is --size-16. No
    role-against-background table has a row for text ON a fill. The fill is alert-ink now;
    both tokens are approved and only the pairing changed.
  - EVERY BUTTON RENDERED THE WRONG COLOUR in Chromium: without `appearance: none` the
    engine blends the author background with its native widget rendering, so #0B6B4F came
    out as rgb(174,202,194) and the label as rgb(72,72,72) instead of #FFFFFF. The whole
    contrast table would have described pairs the product never shows. Invisible to every
    source-level and jsdom test, because both see the declaration.
  - and kit.css never set the document's own ink-on-paper, so anything inside ThemeProvider
    without a landing template inherited the UA's black-on-white.

TWO HARNESS DEFECTS IN THE BROWSER SUITE ITSELF, both of which could have produced a false
PASS rather than only a false failure — which matters because these are the only checks in
the project that can see a computed style at all:

  - `goto(file://…)` + `addStyleTag()` left four buttons at the UA pair while every
    observable said the author rules had won (parsed, matched, parsedOk, variables
    resolving). The same CSS through `setContent` resolves correctly. The sequence is gone.
  - `setAttribute('data-theme', …)` after load invalidated PARTIALLY: the custom properties
    updated to the dark values while the element's computed color and background stayed
    light. A dark-theme assertion could have agreed with a light-theme reading. The theme is
    parsed with the document now.
  - the vacuity guard passed through both, because it checked one background on a non-widget
    element. It now checks a section, a native button AND a native input, and asserts the
    theme under test actually took.
